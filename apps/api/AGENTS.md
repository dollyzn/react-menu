# apps/api (AdonisJS 7)

Read the root `AGENTS.md` first. This file only covers the API.

## Where things go

| Concern | Location |
| --- | --- |
| Routes (grouped by area) | `start/routes/*.ts`, composed in `start/routes.ts` |
| Middleware (named: `auth`, `storeAccess`) | `app/middleware`, registered in `start/kernel.ts` |
| Authorization | `app/abilities/main.ts` (`accessStore`), `app/policies/*` |
| CSRF | `#middleware/cookie_auth_middleware` + `#helpers/trusted_origin`: a write (not GET/HEAD/OPTIONS) that carries the session cookie must come from `FRONTEND_URL` (or `TRUSTED_ORIGINS`; localhost/LAN outside production) by `Origin`, or `Sec-Fetch-Site: same-origin`; else 403 `E_UNTRUSTED_ORIGIN`. Bearer-token and cookieless calls (webhooks) are not affected |
| Input validation (VineJS) | `app/validators/*` (store slugs: `^[a-z0-9-]+$` minus `RESERVED_SLUGS` in `validators/store.ts`, the web's own root paths and the scanner paths its proxy blocks) |
| HTTP layer | `app/controllers/*` (thin: validate, authorize, call service, respond) |
| Business rules, transactions | `app/services/*` |
| Queries, store scoping | `app/repositories/*` |
| Models / migrations / seeders | `app/models`, `database/migrations`, `database/seeders` |
| Responses / errors | `app/helpers/api_response.ts`, `app/exceptions/handler.ts` |
| Realtime channels | `app/helpers/realtime.ts` + authorization in `start/transmit.ts` |
| Notifications and preferences | Templates in `app/notifications/templates.ts` (each with `label`, `description`, default channels `{ push, email }` and `audience`: `staff` or `super`). `NotificationService.notify` always records the bell row, then sends push and e-mail (`NotificationMail`) only where `NotificationPreferenceService.deliveries` allows: per type (`notification_preferences.channels` keeps only the choices that differ from the defaults) and per store (`muted_store_ids` turns both off for that store). `GET/PUT /account/notification-preferences`. Daily summary for managers: opt-in with an hour (`daily_summary`, `daily_summary_hour`), the `SendDailySummaries` job runs every hour (`start/scheduler.ts`, id `daily-summaries`, BUSINESS_TIMEZONE) and sends `DailySummaryMail` (yesterday's sales per managed store not muted, via `ReportService.sales`, plus low stock) once a day (`daily_summary_sent_on`) |
| Orders (pricing, numbering, status machine) | `app/services/order_service.ts`, `app/orders/*`. `GET /orders` is today's board for any member; the history (`?page`) and other days (`?date`) are managers only, and so is `POST /orders/:id/cancel` (it refunds a paid order), except that attendants may drop a POS order still in `pending_payment` with nothing received and no charge waiting on the machine (`OrderService.cancel` `onlyUnpaid`, checked under the lock: 403 `E_NOT_DISCARDABLE`, 409 `E_CHARGE_WAITING`); deliver and receive payment stay front of house. Counter payments are recorded, never assumed: the POS sends `counterMethod` (`cash`/`pix`/`credit`/`debit`, `#enums/counter_payment_method`; credit/debit on a machine outside the system) to create the order paid, or leaves it out (received later, or on the card machine); `POST /orders/:id/payment` ("Receber pagamento") requires `{ method }`; both set `orders.counter_method`, `paid_at` and `paid_by_id` (the detail's `paidBy`, name only). `complete` answers 409 `E_PAYMENT_REQUIRED` for an unpaid order (it no longer marks counter orders paid on hand-over), except "Pagar depois" (fiado): `orders.pay_later_at`/`pay_later_by_id`, set by the POS's `payLater` (needs the phone: 422 `E_PHONE_REQUIRED`) or `POST /orders/:id/pay-later` (front of house, `{ phone? }` when the order has none; not paid, cancelled, `pending_payment` or with a charge on the machine), handed over unpaid; `GET /orders/pay-later` (managers; paginated, `customerName` searches name/phone/number, `sort` `createdAt:asc|desc`/`amountDue:asc|desc`) lists the open ones of any day with `payLaterBy`, `GET /orders/pay-later/summary` gives the count, the total, how many customers, since when and the 12 who owe the most (by phone, or name without one), `GET /orders/pay-later/customers` (managers; paginated, `search` by name/phone/number, `sort` `due:desc`/`since:asc`/`name:asc`) groups them by customer with their orders (the search only finds the customers: what they owe counts all their open orders; `debtor` breaks ties so pages never repeat or skip; LIKE text escaped with `#helpers/like` `containing`), "Receber pagamento" settles one, and `POST /orders/pay-later/receive` (managers; `orderIds` of one customer, else 422 `E_MIXED_CUSTOMERS`, `method`, `amount` = the total on screen, 409 `E_AMOUNT_CHANGED`) settles several at once: locked in id order, a receipt per order for what it owes, the customer and "pagar depois" checked again on the locked rows (409 `E_MIXED_CUSTOMERS`), the ones already paid the same way skipped (a repeat records nothing), `amount` in the answer = what was actually recorded; `markPayLater` also corrects name/phone of one already marked. Sales reports split payments by receipt (`order_receipts`, ADR 0021: every amount received, `orders.amount_paid` their sum, paid when it covers the total, `amountDue` the rest; `markPaid` records them; counter receipts by `counterMethod`, null: paid before it was recorded) plus what is still to receive. Items added while the order is in the queue: `POST /orders/:id/items` (front of house; `OrderService.addItems`: only `received`, 409 `E_ORDER_STARTED` once the kitchen made something, `E_CHARGE_WAITING` with a charge on the machine; priced, stock-checked and consumed like a new order, lines with `added_at`/`added_by_id`; charged now with `counterMethod` (all that is due, checked against `amount`: 409 `E_AMOUNT_CHANGED`; "Receber pagamento" checks its `amount` too) or left to receive, which turns a paid order back to pending; the Idempotency-Key is kept in `order_items.addition_key`; `prepareUnits` locks the orders before their lines) |
| Kitchen queue (pure batching + ingredients) | `app/kitchen/production_queue.ts`, `app/services/kitchen_service.ts` (each batch also has `addonGroups`, from `addonGroups()` in `#models/order_item_addon`). Stock counts, recipes and removed ingredients broadcast `stock.changed` after the commit (InventoryService); item and add-on updates (single and bulk) and turning stock tracking on/off broadcast `menu.changed` (`broadcastMenuChanged`) |
| Inventory (stock, recipes, consumption) | `app/services/inventory_service.ts`: `capacities` (units each item/add-on still makes → `stockLeft` in the public menu), `assertStock` (the whole order against the stock, ingredients locked; on order creation and again before charging an online payment, 422 `E_OUT_OF_STOCK`) |
| Payments (in-app checkout, ADR 0015/0017) | `app/services/payment_service.ts`, gateways in `app/payments/` (`gateway.ts`, `mercado_pago_gateway.ts` on the Orders API: one `ORD…` order per attempt, older numeric Payments API ids still fetched/refunded there; `mercado_pago_client.ts` (a refused card is a 402 with the order; any other refusal logs Mercado Pago's answer, status and path as "Mercado Pago refused a request", then throws `E_PAYMENT_PROVIDER`), `fake_gateway.ts`), attempts in `app/models/payment.ts`; webhook topics `order` and `payment`, signed like the official SDK; a cancelled order's refund first reads the attempt from Mercado Pago and only records it when it was already refunded there (the store's app or panel), and attempts the webhook marked refunded settle the order; an unpaid online order is never cancelled blind: `ExpireUnpaidOrder` first asks the gateway about every pending attempt (`PaymentService.syncPending`; a paid Pix whose webhook never came gets the order paid) and retries instead of cancelling when the gateway can't be reached; Mercado Pago not answering (timeout, dropped connection) is a 504/503 `E_PAYMENT_PROVIDER_UNAVAILABLE`, which the web retries with the same Idempotency-Key (also sent to Mercado Pago, so the retry finds the same charge); a webhook for an Orders API attempt of a pix/card order with no Payment row records it and settles it (paid, or refunded as a duplicate); card fee passed on to the customer (ADR 0022: `stores.card_fee_enabled` + percent for credit/debit, set in `payment-settings`; `#payments/card_fee`; `pay` charges the order plus the fee by the card form's `paymentTypeId`, keeps it in `payments.fee` and `order_receipts.fee`, apart from `amount`, and refuses a different `amount` with 409 `E_AMOUNT_CHANGED`; the public menu and the order's checkout expose `cardFees`); cards ask for 3-D Secure (ADR 0018: `challenge_url` + 40-min `expires_at` on the attempt, `POST /public/orders/:token/payments/sync` reads it again after the challenge) |

## Rules

- Controllers never query models directly for tenant data; go through a
  service/repository method that takes `storeId`.
- Validate route params (`uuidValidator`, `storeExistValidator`), not only bodies.
- Wrap multi-step writes in `db.transaction`; broadcast/notify after commit.
- Money columns are `decimal(10,2)`.
- Lists use `parsePagination` + `pickQueryFilters` (+ `parseSort` with an
  allowlist of column ids; never order by a raw query value) and return
  `ok(paginator.all(), paginator.getMeta())` (camelCase meta: `total`, `perPage`, `currentPage`…).
  Lists the panel filters by options (the order history, items, ingredients)
  also send `meta.facets` (`FacetCounts`) when asked with `?facets=1`
  (`wantsFacets`; the orders validator's `facets`): only the table asks, on
  its first page, so badges, pickers and later pages don't run them. Per
  filter name as the query string sends it (`category_name`, `stock`), how
  many rows each option would show, with the search and the other filters applied but not
  the filter's own choice (one query per filter, built by the same function
  as the list with that filter left out: `historyQuery`, `filtered`). Run
  them one after another, never in `Promise.all` (inside a transaction they
  share one connection).
- Rate limiting: `throttle` must run after `middleware.auth()` or the
  request is limited as a guest (per client IP, `PUBLIC_RATE_LIMIT`, default
  120/min). `request.ip()` is the client's: X-Forwarded-For is trusted from
  local/private proxies only (`#helpers/trusted_proxy`: Caddy, the web's
  SSR), so customers behind the same proxy don't share one bucket. Public order creation has its own
  `orderThrottle` (`PUBLIC_ORDER_RATE_LIMIT`).
- Decimal columns use `@column(decimal)` from `#helpers/columns` so values
  are numbers at runtime.
- Business dates use `BUSINESS_TIMEZONE` (America/Sao_Paulo), not UTC.
- Work that must happen later or be retried (expiry, refunds, push, mail)
  is a job, not a fire-and-forget promise. Dispatch after the transaction
  commits; deduplicate per entity (`.dedup({ id })`) when a retry of the
  request could dispatch it twice.
- External HTTP goes through an injectable client so tests can
  `app.container.swap()` it (`MercadoPagoClient`, `FcmClient`). Push is a
  no-op without FIREBASE_* credentials.

## Tests

Japa functional tests in `tests/functional`, using `.env.test`
(database `react-menu-test`) and `testUtils.db().wrapInGlobalTransaction()`.
Fixtures in `tests/helpers/fixtures.ts`; authenticate with `.loginAs(user)`.
Transmit only subscribes a `uid` with an open event stream: use
`openStream(cleanup)` from `tests/helpers/transmit.ts` in subscribe tests.
Every protected endpoint needs a test proving another store's member gets
403/404.
